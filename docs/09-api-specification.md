## 1. Topology

```
Browser ──(cookie session)──▶ web/BFF  /bff/api/v1/*  ──(Authorization: Bearer <user access token>
                                                        + X-Service-Token: <60 s service JWT>)──▶ api  /api/v1/*
Dedicated host beat ──(HMAC-signed heartbeat, outbound only)──▶ control plane  /api/v1/fleet/heartbeat
```

- Browsers never call the API directly and never hold tokens. BFF routes mirror API paths and add CSRF checks.
- **Service token:** on every call the BFF adds `X-Service-Token`, a short-lived JWT signed with HS256 using `SOS_SERVICE_TOKEN_KEY`: `iss = "sos-web"`, `aud = "sos-api"`, `iat`, `exp = iat + 60 s`, `jti`. The API rejects requests without a valid service token (401), so only the BFF can call it even inside the network.
- **User token:** `Authorization: Bearer <access token>` from the staff OIDC client (school app) or the operator OIDC client (platform admin panel). With Cognito, access tokens have no `aud`; the API checks issuer, `token_use = "access"` and `client_id` against `SOS_OIDC_AUDIENCE` / `SOS_PLATFORM_OIDC_AUDIENCE` (ADR-0018). Control-plane routes accept only operator tokens; tenant routes accept only staff tokens.
- The API trusts nothing from the BFF beyond these two tokens; it re-checks tenant, permission and scope on every call.

## 2. Conventions

| Topic | Convention |
|---|---|
| Base path | `/api/v1` |
| Format | `application/json; charset=utf-8`; dates `YYYY-MM-DD`; timestamps RFC 3339 UTC; IDs UUID strings |
| Language | `Accept-Language: en` or `te` selects message/explanation language. **English first (ADR-0036):** while `SOS_TELUGU_ENABLED` is off every language choice resolves to English through `app.core.languages.output_language()`: `Accept-Language: te` (notifications answer `Content-Language: en`), `language: "te"` in export requests (stored and returned as `en`), a person's `preferred_language: "te"` (kept, returned as `en`; e-mails and sign-in links are English) and a school's `languages` setting (kept, returned and applied as `["en"]`) |
| Telugu fields | **Dormant while Telugu is hidden (ADR-0036).** No `*_te` field is removed from a response and none is required in a request (invariant 12). Responses carry them empty: `""` for a string field (`label_te`, `name_te`, `display_te`, `title_te`, `body_te`, `te` of explanations and routes, letterhead `school_name_te`/`address_te`), `null` where the field is nullable (`summary_te`, certificate `content.class_label_te`). Requests may leave them out: `display_te` (class create), `title_te`/`body_te` (announcements, parent notices) are optional, and a stored value is kept when an update sends one empty. Generated documents (certificates, registers, the correction memo, notices as PDF/PNG, pre-check PDFs, invoices, the certificate of deletion, export watermarks, the data-export `README.txt`) are English only and embed no Telugu font. Student data written in Telugu script is data and is returned as stored |
| Request ID | `X-Request-Id`, always generated by the API (`req_<uuid7 hex>`; a client's own value is ignored so audit records never hold a caller-chosen id, audit 2026-10-06), returned in responses, problem+json and logs |
| Text direction | A JSON body whose text (values or keys) holds a Unicode text-direction control (Bidi_Control: U+061C, U+200E/F, U+202A..E, U+2066..9) → `422 invalid_characters` (audit 2026-10-06; the signed `/edge/` and `/fleet/` routes are exempt). Academic-year and enrolment dates are in the years 2000-2999 (`422`) |
| Idempotency | `Idempotency-Key` required on POSTs that create resources or start jobs; stored 24 h per tenant+user in Valkey (`app/authz/http.py`; control plane: per operator, 16 §8). Same key + same body → original status and `Location`; routes whose response carries C3 text (behaviour notes, raised flags, guardians, change requests) keep only status, the id and headers, never the body, and rebuild the replayed body by re-reading the resource with the caller's current permissions (404 once it is erased; data-protection H-01); same key + different body → `422 idempotency_key_reused`; still running → `409`; the caller's roles, permissions or scopes changed since the first request → `409 idempotency_access_changed` (the stored body is never replayed to different access, audit 2026-10-05) |
| Concurrency | Mutable resources return `ETag`; updates require `If-Match` (missing → `400 if_match_required`, school and control-plane routes alike; a control-plane flag or school override that does not exist yet is created without it); mismatch → `412 Precondition Failed` |
| Pagination | Cursor-based: `?limit=50&cursor=…` (max 200); response `{ "data": [...], "next_cursor": "…" \| null }` |
| Filtering/sorting | Explicit query params per endpoint (e.g., `?section_id=&status=`); `sort=field` or `sort=-field` from an allowlist. Query params carry only IDs, codes, enums, record dates, cursors and page sizes |
| Personal data in URLs | **Never.** Names, phone numbers, emails, dates of birth, addresses, admission numbers, Aadhaar-like input and free-text searches go in a JSON body: searches use `POST /<collection>/search` with the filters, `limit` and `cursor` in the body and the same response as the list (`200`, no `Idempotency-Key`). ALB access logs keep full URLs and cannot redact them (07 §11; `tests/security/test_no_pii_in_urls.py`) |
| Async jobs | `202 Accepted` + `Location: /api/v1/jobs/{id}`; job resource shows `status`, `progress`, `result_url` |
| Rate limits | `RateLimit-Policy` and `RateLimit` header fields (IETF draft-ietf-httpapi-ratelimit-headers-11, which replaced the older `RateLimit-Limit`/`-Remaining`/`-Reset` triple); `429` problem+json `rate_limited` with `Retry-After` (seconds) and `retry_after`. See §2.7 |
| Deprecation | Additive changes only within v1; removals announced with `Deprecation` (RFC 9745, `@<unix seconds>`), `Sunset` (RFC 8594, HTTP-date) and, where a replacement exists, `Link: <...>; rel="successor-version"` headers, sent only on responses that use the deprecated feature, and marked `deprecated` in OpenAPI |

### 2.7 Rate limits (audit 2026-10-05 P2-07; OWASP API4:2023; ASVS 2.2.1, 11.1.4)

Budgets are versioned in `apps/api/app/core/rate_limits.yaml` (invariant 13); the code is `app/core/ratelimit.py`.

- **Algorithm.** GCRA (token bucket) in Valkey: one Lua script per check reads the Valkey clock, checks every bucket of the request plus any sign-in backoff, and charges all of them or none (one round trip, no race between API tasks). Keys `sos:rl:v1:<policy>:<partition>` hold hashes and IDs only. Locally and in CI the same algorithm runs in memory.
- **Layers, in order.** (1) per client IP, in the middleware before authentication and before the body is read; (2) per signed-in person (issuer + subject) or per operator on `/api/v1/platform/*`; (3) per school; (4) the stricter per-route budgets below. Layers 2-4 run in the route guards (`require`, `require_any`, `require_principal`, `require_platform`), after authentication and before the permission check, so refused calls count against the caller's own budgets. **Where budgets are charged (owner decision 2026-10-07).** Budgets per IP, per person, per operator and per school (layer 3) and the per-person route budgets are charged before the permission check: they stop floods, and a refused caller spends only their own budget there (one person is held to 600 units a minute before the school layer of 6000 is charged). Route budgets a whole school shares (`per: school`: `data_export`, `heavy_jobs`, `school_invitations`, `audit_verify`) are charged only **after** authorization: the tenant guards charge `data_export`, `heavy_jobs` and `school_invitations` as their last step, after the permission, scope, step-up and break-glass checks (`ratelimit.charge_school_routes`), and the `POST /audit/verify` handler charges `audit_verify` (`ratelimit.charge`). A member refused with 403 or 428 therefore cannot spend the school's export or job budget and lock out the people allowed to use it; the 429 is unchanged. A test (`tests/security/test_rate_limit_routes.py`) fails when a route's guard does not apply the limiter, an expensive-looking route has no per-route budget, a per-school route budget sits on a route without a tenant guard, or a tenant guard charges per-school budgets before authorization; `tests/api/test_school_budgets_after_authz.py` proves refused members cannot spend them.
- **Cost.** On layers 2 and 3 a read (`GET`, `HEAD`) costs 1 unit and a write 3; per-route budgets count requests.
- **Client IP.** `X-Forwarded-For` is honoured only when the TCP peer is in `SOS_TRUSTED_PROXIES` (the ALB and BFF on the shared tier, Caddy and web on a dedicated host), read right to left skipping trusted hops. The BFF sends the address its own proxy appended (`TRUSTED_PROXY_HOPS`), never the browser's header. A trusted peer that names no client (the BFF's server-side calls) skips the per-IP layer only.
- **Headers.** Every limited response carries `RateLimit-Policy: "user";q=600;w=60, "search";q=60;w=60` and `RateLimit: "user";r=597;t=1, "search";r=59;t=1` for the policies that applied to the caller (`r` remaining units, `t` seconds until the quota is full again). Aggregates shared with others (the IP and school layers) appear only on the 429 they cause; nothing about another school is ever shown.
- **429.** `application/problem+json`, `code: rate_limited`, `Retry-After: <seconds>` and the same number as `retry_after`, and the plain detail "Too many requests. Wait N seconds and try again." The web shows that sentence (`errors.api.rate_limited.bodyWait`). The BFF passes the 429 and all these headers through unchanged. The older limits keep their codes and now also send `Retry-After`: `ai_rate_limited` (Ask, per person, number in `models.yaml`, same GCRA limiter), the invitation e-mail cool-down, the fleet heartbeat (per deployment) and the Tally edge agent (per device).
- **Failure mode.** Valkey unreachable: `fail: open` policies allow the request and the API logs `security.rate_limit.unavailable` (alarmed); `fail: closed` policies (sign-in, invitations, machine paths) and the sign-in backoff fall back to a per-process limiter with the same budget, so an outage cannot be used to brute-force.
- **Sign-in backoff (soft lockout).** Rejected tokens count per client IP, refused sign-ins (`POST /me/login-event` denied, a non-operator at the control plane) per person + IP; after the free failures each attempt waits 1 s, doubling to 15 min, forgotten after an hour or cleared by a successful sign-in. There is no account lockout, so nobody can lock a colleague out from another address. Each failure logs `security.auth.failed` (IDs, reason, `ip_hash`). The BFF does the same per IP for its own sign-in, step-up and callback routes (`signin_failed`, `step_up_failed`, `auth_rate_limited`; 300 starts per 5 minutes per IP).
- **Exempt.** `/healthz`, `/readyz` and CORS preflight (`OPTIONS`). Every BFF call carries a user token, so there are no unlimited service-only calls; break-glass routes have a generous budget.

## 3. Errors (RFC 9457 problem details)

```json
{
  "type": "https://docs.schoolos.example/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_error",
  "detail": "2 fields need attention",
  "instance": "/api/v1/students/0192f…/values",
  "request_id": "req_01J…",
  "errors": [
    { "field": "value_date", "code": "date_in_future", "message_key": "errors.date_in_future" },
    { "field": "attribute_key", "code": "aadhaar_full_number_rejected", "message_key": "errors.aadhaar_last4_only" }
  ]
}
```

| Status | When |
|---|---|
| 400 | Malformed request |
| 401 | Not authenticated / token expired |
| 403 | Authenticated but lacking permission (**only** when existence of the resource isn't sensitive); `code: tenant_suspended` when the school is suspended (except the owner's and principal's Plan & billing and full export routes, 16 §5.5); `code: no_membership` for an `X-Active-Tenant` the user does not belong to; `code: mfa_required` when a privileged role signs in without MFA (ADR-0018) |
| 404 | Not found **or** outside caller's tenant/scope (never reveal existence) |
| 409 | State conflict (e.g., approving a non-pending request) |
| 412 | ETag mismatch |
| 413 / 415 | File too large / unsupported type |
| 422 | Validation errors |
| 428 | Step-up authentication required (`code: step_up_required`): MFA and `auth_time` within 5 minutes; the BFF re-authenticates with `prompt=login` |
| 429 | Rate limited (`code: rate_limited`, with `Retry-After` and `retry_after` in seconds, §2.7), AI question limit (`ai_rate_limited`) / budget exhausted (`ai_budget_exhausted`) |
| 5xx | Server errors, no internals exposed |

Students notes (M1, as built):
- **Scope:** scoped holders (class teacher, subject teacher) reach only students actively enrolled in their sections/classes in the **current** academic year; everything else, including other schools' ids, is `404`.
- **Sensitive (C3) values** are omitted for callers without `student.read_sensitive` and shown as `"••••"` with `masked: true` for holders (`sensitive_revealable: true`); `POST …/sensitive-reveal` with `{"attribute_key": …, "value_id"?: …}` or `{"attribute_key": "guardian_phone"|"guardian_address", "guardian_id": …}` returns one value (`display` e.g. `XXXX XXXX 1234`, `+91 98765 43210`), is audited (`student.sensitive_revealed`) and sent with `Cache-Control: no-store`.
- **Aadhaar (US-303):** any request body field (including `POST /students/search`, and the deprecated `query` parameter) holding a full Aadhaar number is refused before other validation, except the `value` of a typed `apaar_id` entry and the top-level `apaar_id` of `POST /students/search` when either is exactly 12 digits (FR-STU-015/016, ADR-0037): `422` with `{"field": "<path>", "code": "aadhaar_full_number_rejected", "message_key": "errors.aadhaar_last4_only"}` per field. `aadhaar_last4` accepts exactly 4 digits.
- **Identity attributes:** the admission-register value can be recorded once (unverified, so the canonical value is `provisional`); replacing or verifying it needs a change request (`403 identity_change_required`). Observations from other sources are accepted and appear as `conflicts`. Re-sending an identical value is a no-op (same id).
- `POST /students`, `POST …/values`, `POST …/guardians`, `POST …/enrollments` accept `Idempotency-Key`; `GET /students/{id}` returns `ETag` (student version), which `POST …/values` accepts as an optional `If-Match`.
- **Scope for enrolment writes:** a scoped holder may move a student only into a section they reach (else `422 section_id not_found`); another student's enrolment id under this student's path is `404`.
- Search (`POST /students/search`; send `next_cursor` back as `cursor` with the same filters): `query` tokens are name text (EN/TE), class/section (`9b`, `9-B`, `IX-B`), class number (`9`) or admission number (prefix, exact first); results carry `class_section` and `match: {field, score}`; cursor pagination.

Promotions notes (M1, FR-TEN-011, US-202 AC2; owner decisions 2026-09-27; as built in `app/students`):
- **`{year_id}` is the year being closed** (the source). Body of `:preview` and `:commit`: `{"to_academic_year_id", "held_back_student_ids"?: [...], "section_map"?: [{"from_section_id", "to_section_id"}]}`; `:commit` also takes the preview's `plan_fingerprint` (optional). The target year must start later (`422 not_later`, `same_year`, `not_found`); held-back ids must be enrolled in the source year (`422 not_in_year`); a `section_map` entry applies to the students of its source section whose target class is the class of its target section (at most one per pair, `422 duplicate`).
- **Plan:** every active enrolment of the source year: class N → N+1 by `sort_order`; held-back students → the same class again; the last class → `graduated` (record status, no new enrolment); students whose record status is `left` or `graduated`, or who are already active in the target year, are `skipped` (nothing changes). Target section: the `section_map` entry, else the section with the same name in the target class. `:preview` (`200`, writes nothing) returns `counts`, `groups` (per source section, outcome and target section, with labels such as `IX-A`), `problems` (`no_target_section` with source section, target class and count), `students` (ids, outcome, target section, `reason`), `plan_fingerprint` and `can_commit`. Ids only, no names.
- **`:commit`** (`201`, `Idempotency-Key`, `Location: /academic-years/{year_id}/promotions`) applies the plan in one transaction and returns the promotion (`id`, `status`, `counts`, `committed_at`, `undo_until`, `can_undo`). Refusals: `409 promotion_already_committed` (undo the earlier one first), `409 promotion_plan_changed` (fingerprint differs), `409 nothing_to_promote`, `409 structure_archived` (a target section, its class or the target year was archived), `422 no_target_section` (field `section_map`). Audit `promotion.committed` (promotion id, year ids, counts); outbox `student.values.changed` (`enrollment` marker) for every moved student.
- **`:undo`** (`200`, no body) within 24 h of the commit; `409 no_promotion`, `409 promotion_undo_expired`, `409 promotion_has_dependents` when an enrolment it closed or opened changed afterwards (e.g. a roll number was corrected), a graduate's status changed, or a student was enrolled again in the source year (the import-revert rule); `409 structure_archived` when the source year (or a section or class of it) was archived since. Removes the enrolments it opened, reopens the ones it closed and restores graduates' previous status. Audit `promotion.undone`. After an undo the year can be promoted again.
- `GET /academic-years/{year_id}/promotions` lists the year's promotions, newest first, with `can_undo` and the display names of who committed and who undid each (`committed_by_name`, `undone_by_name`; never emails).

Certificate notes (M3, as built; data model 05 §5.7). The stories and requirements are proposed from the roadmap scope and still need PO confirmation.
- **Request** (`POST /students/{id}/certificates`):
  - `certificate_type` is one of `transfer`, `bonafide`, `study`, `conduct`.
  - `inputs` are the type's declared inputs (`GET /certificates/types`), such as leaving date, reason, promotion and conduct for a TC, or purpose for a bonafide certificate. Unknown keys, bad choices and control characters give `422` with a per-field code. A full Aadhaar number in free text is refused.
  - The certificate is built only from the canonical record (BR-01). An open blocker DQ finding on a printed field, an empty printed field, an inactive student, no enrolment or no current year gives `409 certificate_blocked`. Its `errors[]` carry the `code` (`dq_blocker`, `missing_value`, `student_not_active`, `no_enrolment`, `no_current_year`, `transfer_certificate_exists`, `change_request_pending`) with `attribute_key`, `finding_id` and `rule_id`. The preview returns the same list as `blockers`, plus `warnings` for provisional values. A correction waiting for approval on a printed field is the blocker `change_request_pending`; when it is the only one, issuing and approving answer `409 change_request_pending`.
  - A bonafide, study or conduct certificate is issued at once: serial number, register entry and PDF queued. A TC is saved as `pending`. A second live TC gives `409 transfer_certificate_exists`.
- **Approve** (TC and TC duplicates): errors are `403 self_approval_forbidden`, `428 step_up_required`, `412` for a stale `If-Match`, `409 certificate_not_pending`, and `409 certificate_blocked` / `change_request_pending` (checked again), `409 requester_inactive` (the person who prepared it is no longer an active member; reject still works), and `409 certificate_draft_changed` when `draft_sha256` does not match what the certificate would print now. `GET /certificates/{id}` returns `draft_sha256` for a pending request (SHA-256 of the content it would freeze, serial and issue date left out; a duplicate's is its original's frozen hash; `null` in lists and once decided) (A-11). In one transaction the TC gets the next serial and its register entry, and the student's enrolment ends on the leaving date (`422 leaving_date_before_enrolment`). The requester is notified.
- **Reject**, withdraw and cancel:
  - Reject and cancel need a reason of 10–1000 characters.
  - Withdraw by anyone else gives `403 not_requester`.
  - Cancel gives `409 certificate_not_issued` unless the certificate is issued. A cancelled certificate keeps its number, is marked CANCELLED on the print view and in the registers, and its PDF document is archived. Cancelling a TC does not re-admit the student.
- **Duplicate** (of an issued original): copies the frozen content and is marked DUPLICATE with the original serial and a copy number. It has no serial of its own. `409 certificate_not_issued` or `duplicate_pending`. A TC duplicate needs approval like the TC.
- **Response** `CertificateOut`:
  - ids and type, `status`, `requires_approval`, `inputs`;
  - `serial` and `academic_year_id`;
  - `student_name` and `admission_no` (for the list);
  - `content` (the frozen printed values once issued: EN/TE labels, values, details, blanks for official-format fields not yet filled);
  - the requester, decider, issuer and canceller (membership ids), with times;
  - `decision_note`, `cancel_reason`, `document_id`, `pdf_status` (`none|queued|ready|failed`), `version`;
  - for the caller: `can_approve`, `can_withdraw`, `can_cancel`, `can_duplicate`.
- **Print view and registers**:
  - Bilingual (EN/TE) A4 pages rendered by the API: certificates are portrait, registers landscape.
  - Every value is HTML-escaped and Aadhaar-masked. There are no scripts, only style blocks pinned by hash in the CSP. Headers are `Content-Disposition: inline` and `Cache-Control: no-store`. The BFF leaves the API's CSP on these paths (`proxy.ts` `OWN_CSP_PATHS`).
  - A pending certificate prints as DRAFT with no serial.
  - Registers list every issued serial of the year in order, including cancelled ones. Rows are capped at 5,000 (`register_max_rows`).
  - Audited as `certificate.print_viewed` and `register.viewed`.
  - `?check=true` on a register route only checks that it can be printed now (step-up, year, type, row cap) and answers `204` without the page; it is not audited. The registers screen checks first and then links to the print view, so one view is audited once.
- **Download** gives `{url, expires_at, filename}` (`attachment`, ≤ 5 min), or `409 pdf_not_ready` / `document_not_ready`. Audited as `certificate.downloaded`.
- **Scope**: certificates are reached through their student. Holders of a scoped role see only their sections' students. Another school's id, or a student out of scope, gives `404`.
- **No public verification route** (QR or serial lookup). It would need an ADR (PO question).

Imports notes (M1, as built; US-401, FR-IMP-001..007):
- **Upload first** with `POST /documents/uploads` (purpose `import_file`: XLSX or CSV/Google Sheets CSV export, ≤ 10 MB) and `POST /documents`; `POST /imports` accepts the document once it passed the virus scan (`409 document_not_ready` before; `413`/`415` for size/type; `409 import_exists` when the file already has a live batch). Parsing, validation and commit run in workers (queue `ingest`); the body carries `job_id`, `Location` points at the batch, whose `status` moves `uploaded → parsing → parsed → validating → validated → committing → committed` (`failed` with `error_code`, e.g. `header_not_found`, `too_many_rows`, `file_too_complex`).
- **Formulas are never evaluated**: a formula cell (or text starting with `=`/`@`) is kept as inert text; mapped, it is a row error `formula_not_evaluated`.
- **Staged sheet** (US-401 AC5/AC6; FR-IMP-008, FR-IMP-009): `GET …/sheet` pages the uploaded file (100 rows by default, at most 200) as `columns` (`index`, `letter`, `header`, `target`, `restricted`, `editable`) and `data` rows (`row_no`, `cells` of `{value, edited, restricted, formula}`, `status`, `errors`, `warnings`); `editable`/`read_only_reason` (`committed`, `reverted`, `in_progress`, `failed`); `edited_cells`. Restricted (C3) columns (mapped to, or suggested for, a C3 field) never carry values; Aadhaar-like numbers are masked. `PATCH …/sheet/rows/{row_no}` changes up to 60 cells of one row (`null` or blank clears): `412` when the ETag is stale, `409 import_not_editable` once committed, reverted or while a job runs, `409 import_not_ready` / `file_missing`, `404` for a row the file does not have, `422` (`aadhaar_full_number_rejected`, `control_characters`, `too_long`, `column_restricted`, `unknown_column`, `duplicate_column`; values are never echoed). The raw file is kept; the edit is stored encrypted and applied to every later read, re-check and the commit; a `validated` batch re-checks the row at once. Audit `import.cell_edited` per cell. The PATCH is guarded by `If-Match` alone (no `Idempotency-Key`): an edit that changes a cell moves the ETag on, so a replayed request answers `412` (and one that changes nothing is a no-op), never applying twice. `GET …/sheet/export` returns the staged sheet with its edits (CSV UTF-8 with BOM, or XLSX with text cells and the watermark), masked and formula-neutralised; restricted columns are empty without `student.read_sensitive`; audit `import.sheet_exported`.
- **Mapping**: columns are suggested from English/Telugu headers; a saved template with the same headers is applied automatically (`mapping_template_id`). `PUT …/mapping` replaces the mapping (`{"columns": [{"index", "target"}]}`) and clears earlier results; validate again with `POST …/validate`.
- **Rows**: `errors`/`warnings` are `{field, code, message_key, ref?}` (e.g. `missing`, `invalid_date`, `ambiguous_date` (warning), `duplicate_in_file` with `ref` = other row, `identity_change_required`, `no_matching_student`, `section_out_of_scope`, `aadhaar_full_number_rejected`). Rows never show C3 values, only `sensitive` keys. The admission number matches existing students (`action: update`); only `admission_register`, `tc_incoming` and `manual_entry` rows may create students (and need `student.create`).
- **Commit** is all-or-nothing (`409 import_has_errors` unless `skip_error_rows`); the worker re-reads and re-validates the file inside the commit transaction (failure → back to `validated` with `error_code`). Audit `import.committed`, outbox `import.committed {batch_id, student_ids_count}`, notification `import.committed` to the requester. **Revert** within 24 h (`409 revert_window_closed`), refused with `409 import_has_dependents` when records from the batch were changed or are referenced since (a student it created changed, one of its values was superseded, a value it replaced is a verified or admission-register identity value, or another record such as a change request points at a student it created). In one transaction: the batch's values on existing students are withdrawn (history kept) and the values they replaced become current again; the students it created are removed. Audit: `import.reverted` (counts: `students_removed`, `values_withdrawn`, `values_restored`) plus the students module's own events, `student.values.withdrawn` per existing student that lost values, `student.value.recorded` per restored value and `student.removed` per removed student (`reason: import_reverted`, `import_batch_id`; keys and counts only, never values); outbox `import.reverted {batch_id}` (drives the DQ re-run); notification `import.reverted` to the person who uploaded the file when someone else reverted it (none when they reverted it themselves or are no longer an active member).
- **Raw file retention** (FR-IMP-007, docs/05 §13): the uploaded file is kept while a job uses it and for 90 days after commit (`DELETE /documents/{id}` → `409 import_in_progress` / `import_file_retained`, the imports module's delete guards). The daily job then deletes it through the documents retention primitive `documents.delete_for_retention(reason="import_raw_file")`: the same delete path as `DELETE /documents/{id}` (delete guards, evidence check, objects purged after commit) with the system as actor; audit `document.deleted` (`reason: import_raw_file`) and `import.raw_file_deleted` per batch. The parsed rows stay.

Exports notes (M1, as built; US-501 AC4, US-901, FR-EXP-001..004, SEC-017; access and step-up per ADR-0021):
- **Pre-check** (`POST /exports`): `profile_key` is a DQ profile with an export layout (`cisce-registration-2026` → `export.board`, `udise-plus` → `export.portal`; `GET /export-profiles` lists them with the "ready to enter" field order and `allowed`); `scope` = `section_ids` (≤ 100) or `class_ids` (≤ 50) of the current year, empty = every student you can see; `format` ⊆ `xlsx`, `pdf` (default both); `language` `en`|`te`. The students you can reach are frozen on the export (≤ 2,000; `422 no_students` / `too_many_students`; another school's section/class → `422 not_found`). The worker re-runs the DQ checks for the profile, then builds an XLSX (Summary, Findings blockers first, Ready to enter in the profile's field order with a status column) and an A4 PDF (headless Chromium, queue `pdf`). Findings show the masked values the DQ engine stored; every pre-check needs step-up (`428 step_up_required`); restricted (C3) fields of the ready sheet (e.g. UDISE+ `category`) show `••••` unless `include_sensitive` (needs `student.read_sensitive`, else `403 sensitive_not_allowed`; the `export.requested` audit event then lists them in `sensitive_columns`); Aadhaar-as-printed fields are never exported and `aadhaar_last4` appears only as `XXXX XXXX 1234`.
- **Student list** (`POST /exports/student-list`, step-up): `columns` are attribute keys or `class`, `section`, `roll_no` (≤ 60; unknown or Aadhaar-as-printed → `422 column_not_exportable` per column); `format` `csv` (UTF-8 with BOM, watermark on the first line) or `xlsx`.
- **Every file**: bilingual watermark (English only while Telugu is hidden, ADR-0036) "Generated by SchoolOS for internal checking"; every cell NFC, Aadhaar-like numbers masked (Verhoeff) and cells starting with `=`, `+`, `-`, `@`, tab or CR prefixed with `'` (SEC-017); XLSX cells are written as text.
- **Status and download**: `202` + `Location: /api/v1/exports/{id}`; `status` `queued|running|ready|failed|expired`; the requester gets `export.ready`/`export.failed` notifications. `download-url` returns `{url, expires_at, format, content_type, filename}` (≤ 5 min, `attachment`); `409 export_not_ready|export_failed|export_expired`; `404` for other schools' exports, for other members' exports unless you hold `export.read_all` (details) or `export.download_any` (files), and for a format the export does not have. Files are deleted 7 days after they are ready (make a new export). Audit: `export.requested`, `export.completed`, `export.failed`, `export.downloaded` (with `own_export` and `requested_by_membership`), `export.expired` (IDs and counts only). `Idempotency-Key` accepted on both POSTs.
- **Whose exports** (ADR-0021): `GET /exports` returns your own exports by default (`requested_by=me`); `requested_by=all` returns every export of the school (`export.read_all`: owner, principal, office admin). Each `ExportOut` carries `requested_by` = `{membership_id, display_name}` (display name `null` if the account is no longer visible; nothing else about the person), `own` (you requested it) and `can_download` (your permissions allow a download link now; a `428` can still follow and the export must be `ready`). `export.download_any` (owner only by default) downloads someone else's export, always with step-up.

Admin console notes (M1, as built; US-1201, FR-ADM-001, FR-ADM-002, BR-08; data model 05 §7.3):
- **Full export** (`POST /admin/tenant-export`): the worker (queue `exports`) builds one ZIP: `README.txt` (EN/TE), `manifest.json`, `records/<table>.csv` + `.json` for every record table (school, structure, staff and roles, students with the values from every source, enrolments, guardians, promotions, change requests, data-quality runs and findings, import batches and templates, document metadata, retention settings), every uploaded document version that passed the virus scan (`documents/<id>/v<n>.<ext>`, SHA-256 checked) and `audit/audit-log.csv` (the audit export's columns). Restricted (C3) values, guardian phone and address are `••••` unless `include_sensitive`; the Aadhaar-as-printed fields are never exported; `aadhaar_last4` only as `XXXX XXXX 1234`; cells neutralised against formulas (SEC-017) and Aadhaar-like numbers masked. The archive is streamed to the private bucket (SSE-KMS, never the worker's disk) and deleted 24 hours after it is ready (hourly purge; `TenantExportOut.expires_at`). The requester gets `admin.tenant_export.ready` / `.failed` (EN/TE). Every holder of `tenant.export_all` sees and downloads every full export of the school (`own` says whose it was). Audit: `admin.export.requested|completed|failed|downloaded|expired` (IDs, codes and counts only).
- **Suspended schools** (16 §5.5): the four `/admin/tenant-export` routes stay open for the owner and principal (the route permission still applies: the principal gets 403 `forbidden`, not `tenant_suspended`); `/admin/retention` does not.
- **Retention** (`GET/PUT /admin/retention`): `categories` = `key`, `days` (the school's period), `default_days`, `min_days`, `max_days`, `configurable`, `enforced` (a job deletes the data), `is_default`; `version`, `updated_at`, `updated_by`. `PUT {"rules": {"import_raw_files": 30}}` sets the configurable categories; one left out goes back to its default. Bounds live in `app/admin/retention.yaml`; the jobs `imports.purge_raw_files`, `exports.purge_expired` (via the export's `expires_at`) and `notifications.purge_read` read the school's period. Audit `admin.retention.updated` (category, from/to days).

### Break-glass (support access; US-103, FR-OPS-004, 07 §6.4)
A request pulled from the control plane and the grant it becomes are one object (`ops.break_glass_grants`), so `{request_id}` and `{grant_id}` name the same row. Another school's ID → 404.
| Method | Path | Permission |
|---|---|---|
| GET | `/breakglass/requests` (`status`, `limit`, `cursor`) · `/breakglass/requests/{request_id}` | `breakglass.approve` (the list first pulls new requests) |
| POST | `/breakglass/requests/{request_id}/approve` · `/deny` | `breakglass.approve` (step-up); approver ≠ the person who gets access |
| POST | `/breakglass/grants/{grant_id}/revoke` | `breakglass.approve` (step-up); also ends emergency access |
| POST | `/breakglass/support-session` (`platform_request_id`) → `grant_id`, `tenant_id`, `expires_at`, `scope` (**built**, ADR-0023) | `session.authenticated`, but only a SchoolOS support principal (support client of the operator pool) on its own active grant; school staff get `403 breakglass_only`; another membership's request `404`; ended grant `409 breakglass_grant_inactive`; sign-in within 5 min (`428`). Audited `breakglass.session_started` in the school's chain and the control-plane chain |

### Notifications (FR-NOT-001)
Own notifications only (another person's or school's ID → 404). Titles and bodies are rendered in the `Accept-Language` language (`te` or `en`, default `en`; always `en` while Telugu is hidden, ADR-0036; `Content-Language` says which).
| Method | Path | Permission |
|---|---|---|
| GET | `/notifications` (`unread`, `limit`, `cursor`) | authenticated |
| GET | `/notifications/unread-count` | authenticated |
| POST | `/notifications/{id}/read` · `/notifications/read-all` | authenticated |

Templates (English and Telugu, `app/notifications/templates.yaml`): `change_request.submitted|approved|rejected|expired`, `dq.run.completed`, `import.validated|committed|reverted` (`import.reverted` goes to the uploader only when someone else reverted the import), `export.ready|failed`, `admin.tenant_export.ready|failed` (full export; `hours` the link stays valid), `extraction.batch.ready|failed`, `document.quarantined`, `breakglass.requested|approved|denied|revoked|expired|emergency`, `certificate.approval_requested|approved|rejected`, `circular.read_ready|needs_review`, `task.assigned|due_soon|overdue`, `insights.flag_raised|flag_assigned|flag_overdue`, `tally.agent_silent`. Bodies carry ids and counts, never student names or values. Every template has a producer in app code (`apps/api/tests/notifications/test_templates.py`). There is no announcement notification (owner decision 2026-10-04): platform announcements reach schools only as the banner (`GET /announcements`), and the control plane never writes school notifications (ADR-0020); the former `announcement.new` template, which nothing sent, was removed. A `resource_type` the web app has no screen for is shown without a link.

**Email** (docs/03 §5, Amazon SES; off unless `SOS_EMAIL_PROVIDER` is `ses`, or `fake` locally): a staff invitation email (`invitation.staff`, English or Telugu by the person's preferred language (English while Telugu is hidden, ADR-0036), `app/notifications/email_templates.yaml`) is queued when `POST /users` invites someone who has an email address, and on `POST /users/{user_id}/invitation-email`. The request only writes the outbox event `notification.email.requested` (`message_id`, `user_id`, `template_key`; never an address) and the audit event `notification.email_requested`; the worker task `notifications.send_email` reads the address, language, school name and acceptance deadline and sends after commit (retries while SES is unavailable; skips people who accepted, were removed or whose invitation expired). Addresses, subjects and bodies are never logged. Owner invitations from the control plane, billing reminders and usage alerts are not emailed yet.

| Area | Paths (under `/api/v1`) | Protection |
|---|---|---|
| Operator session, dashboard | `/platform/me`, `/platform/dashboard` | `require_platform(...)` |
| Schools and provisioning | `/platform/tenants…` (list, detail, provision `201`, activate, owner-invite resend, suspend, reactivate, `offboarding` + `offboarding:approve`; offboarding progress `GET …/offboarding`, `offboarding:confirm-export`, `offboarding:confirm-teardown`, `GET …/deletion-certificate/download-url`; docs/16 §5.5.1) | `platform.tenants.*` |

Control-plane edits take `If-Match` as an **optional** precondition (house pattern: tenant billing account, deployments, announcements, support tickets and, since 0.12, draft plans): without it the edit applies; with a stale ETag it answers `412 precondition_failed` and changes nothing. A plan's ETag is `row_version` (its edit counter), not `version` (its catalogue version).

These routes are not mounted when `SOS_DEPLOYMENT_MODE=dedicated` (requests get 404). The route-enumeration test accepts exactly one guard per route: `require()` (tenant routes; `session.authenticated` for member-only routes), `require_platform()` (only under `/api/v1/platform/`) or `require_fleet_signature()` (only the heartbeat); only `/healthz` and `/readyz` are public.

## 6. Internal domain events (for workers and future webhooks)
