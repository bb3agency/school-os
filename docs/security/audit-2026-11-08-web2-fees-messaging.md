## Verified clean (no finding)

- Money arithmetic: `toPaise`/`fromPaise` add and compare whole paise (12-digit rupees stay under 2^53); the counter, allocation, refund and payment-link amounts never use floating-point rupees. Display goes through `formatInr` (`en-IN`, `₹1,25,000.00`, Latin digits); negative Tally balances show the sign plus an "Advance" pill (colour not the only signal). `estimatedCost` is display-only and rounded to paise.
- Receipt numbers are shown exactly as the API sends them (counter saved panel, receipt page, approvals, daily report, refund voucher numbers), never rebuilt or reformatted.
- Day close: the counter shows "The day is closed" from `GET /fees/status` and offers no form; "Close day" is offered only to `fee.manage` and only while the day is open; the date picker stops at today.
- Maker-checker: approve/reject buttons come from the server's `can_decide`, own requests are listed separately with "Withdraw" only; approving and rejecting require step-up and send `If-Match`; 403 `self_approval_forbidden` has a plain message.
- Counter: one Idempotency-Key per payment form, synchronous double-submit guard (WD-06), UTR/cheque/bank-reference checks, `utr_in_use` shown on the UTR field, search terms only in POST bodies.
- Payments: key secret and webhook secret only in dialog memory; key id format checked; connection status drives what is offered; reconciliation uses cursors.
- Tally: read-only screens; amounts and balances use the shared formatter; the connector enrol code is shown once.
- Messaging: opt-in schema needs an evidence document for a signed form; quiet hours equal start/end refused (D56); no-message dates parsed as real DD/MM/YYYY dates.
