# ADR-0024: Resumable school provisioning instead of one transaction

| Field | Value |
|---|---|
| Status | Proposed |
| Date | 2026-09-27 |
| Deciders | Founder / product owner |
| Amends / supersedes | Would amend requirement FR-PLT-002 (03-TRD §3.12) wording "in one transaction"; builds on [ADR-0013](ADR-0013-cross-tenant-access-and-platform-privilege-separation.md), [ADR-0017](ADR-0017-platform-admin-panel-architecture.md), [ADR-0020](ADR-0020-control-plane-boundaries-and-guaranteed-audit-copies.md) |

## Context

FR-PLT-002 says shared-tier provisioning MUST, "in one transaction and idempotently", create the
tenant, its keys, audit chain head, system roles, owner invite, billing account, subscription and
deployment. It cannot be one transaction:

- the tenant row, deployment, billing account, subscription and the owner invite are written by
  `sos_platform` (control plane; tenant rows only through allowlisted definer functions);
- the wrapped DEK/HMAC key and the system roles are written by `sos_app` inside the new school's
  `tenant_session` (RLS), which `sos_platform` must never be able to do (CLAUDE.md §6.1);
- the key is generated by KMS, an external call.

One transaction would need `sos_platform` privileges on tenant tables or a new definer function
that writes keys and roles, both ruled out without a much bigger decision. The implementation up
to 0019 did step 1 atomically and then ran the other steps idempotently, resuming by code and
school name (03 §5 marks FR-PLT-002 "Partial"; roadmap 14 lists the question as open;
`.handoff/HANDOFF.md` §3.6). Failure modes of that version:

| Failure | Effect before this ADR |
|---|---|
| Crash between the steps | School stuck in `provisioning`; nothing records it; the operator cannot tell a stalled provisioning from one waiting for go-live |
| Keys created, invite step failed | Go-live allowed (the database only needs a key): a live school with no owner |
| Retry with the same code and name but a different owner or plan | Silently accepted; the retry's owner gets the invite although step 1 recorded the first request |
| Retry with the same Idempotency-Key after a process crash | `409 idempotency_in_progress` for 24 h (the key store never saw completion); with a new key only the code-and-name resume helped (unchanged: the key store still answers 409 for that key; the same request with a new key now resumes by fingerprint) |
| Two concurrent submissions (two operators or keys) | One school, but the second gets `409 duplicate` and two runners can race on the key insert |
| Dedicated tier, response lost | Retry with a new key gets `409 duplicate` |

## Decision

1. Provisioning is a **persisted state machine** in `platform.provisioning_runs` (migration
   `0020_provisioning_runs`), one row per school: `registered` → `initialised` → `completed`, or
   `failed` (with `failed_step` and an error code). Step 1 (tenant row via
   `core.provision_tenant`, deployment, billing account, subscription, platform event, the run)
   stays one platform transaction; step 3 (owner invite, `tenant.owner_invite_created`, the
   school-chain `tenant.provisioned` via `platform.tenant_audit.enqueue`, run `completed`) is one
   platform transaction; step 2 (keys and roles) is one tenant transaction.
2. **Idempotency by request fingerprint**: the run stores the SHA-256 of the canonical request.
   The same request again (any key, any operator) resumes or replays; the same code with a
   different request is `409 duplicate`.
3. **Lease with fencing**: one runner at a time (`provisioning.lease_seconds`, billing.yaml);
   every state change is conditioned on the runner's lease; a crashed runner's lease expires.
4. Each tenant-side step is **idempotent and serialised** per school (`initialise_tenant` takes a
   transaction-level advisory lock; the key is kept if present; hooks are idempotent).
5. A failure is recorded (`failed`, `tenant.provisioning_failed`) and an operator resumes it
   (`POST /platform/tenants/{id}/provisioning:resume` or the same request again;
   `tenant.provisioning_resumed`). The owner invite parameters are kept in the run **only until
   the invite exists** (a CHECK clears them on completion) so a resume needs no form.
6. **Go-live is refused** (`409 provisioning_incomplete`) until the run is `completed`.
7. No new database privilege: the run table is in schema `platform` (`sos_platform` SELECT,
   INSERT, UPDATE); `sos_platform` gains nothing on tenant tables; no new definer function or
   `definer_access` policy.
8. FR-PLT-002 should be reworded on acceptance to: "... MUST create ... **atomically per step and
   idempotently, as a resumable provisioning whose incomplete state is visible and blocks
   go-live** ...", and 03 §5 / 14 updated to "Built".

## Consequences

- Good: every failure mode above converges on exactly one school, key, owner membership and
  school-chain event; operators see and resume stuck provisionings; no live school without an
  owner; no new privilege.
- Bad / costs: a new platform table holding the owner's display name, sign-in subject and optional
  email until the invite exists (staff contact data, not student data; never returned by the API);
  a crashed request blocks retries for up to the lease length (120 s).
- Follow-up work: amend 03 FR-PLT-002 and its §5 status, 14 roadmap item; web: provisioning state
  and a "Resume provisioning" action on the school detail page (en/te); consider a sweep that
  alerts on runs left unfinished for more than a day.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| One transaction via a new definer function writing keys and roles | Puts key and role creation in a definer path callable by the control plane; widens ADR-0013's allowlist for convenience; KMS call inside a long DB transaction |
| Give `sos_platform` write access to `core.tenant_keys` / roles | Breaks CLAUDE.md §6.1 |
| Keep "resume by code and name" | Leaves the failure modes in the table above |
| Celery saga (steps as tasks) | Same state is still needed; adds queue latency to an interactive wizard; possible later for retries without an operator |
